# Product Brief: DBServices Agent 資料平面

## Executive Summary

DBServices 今天是一套薄的多資料庫存取層：C# SDK、`IQuerySession`、REST、動態 GraphQL、CLI。它讓應用用同一套介面存取 SQLite、SQL Server、MySQL、Oracle、PostgreSQL。Agent 若要查這些庫，仍得自己寫 SDK、拼 REST，或讀懂 GraphQL。

市場上的 Agentic AI 已經會呼叫工具。缺的不是另一個查詢引擎，而是一個可被外部 Agent 安全呼叫的資料平面：工具對應既有的 Session Call，連線由伺服器設定，寫入預設關閉，每次呼叫留稽核。DBServices 的重新定位是這件事。

一句話：DBServices 是可被 Agent 安全呼叫的資料與報表平面。資料仍由現有 Session 與提供者負責；AI 負責理解意圖、選擇已註冊工具、套用報表範本、撰寫說明。第一個可驗證增量只做唯讀 MCP。對談查資料、拖拉報表範本、對談套版，都排在這條平面穩定之後。

## The Problem

整合方已經用 DBServices 接上業務庫。當他們把 Agent 放進工作流程，Agent 仍面對三個缺口。

第一，沒有穩定的工具面。REST 是資料表 CRUD，條件是單一鍵值、主鍵是整數 Id。Session 裡其實已有 `tables`、`fields`、`get`、`query`、`count`、`exists`，但它們沒有以 Agent 能發現的工具形式露出。Agent 於是傾向直接寫 SQL。`sql` 這個 Call 存在，卻把方言、注入與越權交給模型。

第二，連線秘密容易漏進提示。EZIE 元件已經要求只用 `connectionId`，不在設定裡放明文連線字串給呼叫端。Web 與 GraphQL 的連線在伺服器組態。Agent 工具若接受呼叫端傳入的連線字串，這條界線就破了。

第三，報表仍是人工作業。業務人員要的是「這個月的銷貨，用月報格式」。今天的產品停在查列與 JSON。沒有制式範本，也沒有一個解析步驟知道該用哪個資料來源、哪份範本、哪些參數。這個缺口是真的，但它依賴前面的工具面先存在。

現況的成本是：每個 Agent 專案各寫一套資料存取，五種資料庫的差異被重複處理，而且查詢路徑無法稽核。

## The Solution

在 API 層新增一個 MCP 宿主。它是新的客戶端，與 REST、GraphQL、CLI 並列。宿主向外部 Agent 廣告唯讀工具，工具實作就是現有的 Session Call。資料庫由 `DbServiceFactory` 依 `ServerType` 建立 `IDbService`。宿主、路由、工具描述都不出現某一家資料庫的型別。

P0 的體驗是：整合方在伺服器設定具名連線；外部 Agent 列出工具；依序呼叫列出資料表、列出欄位、依鍵值查詢；拿到列資料。寫入與自由 SQL 不在廣告清單裡。每次呼叫留下工具名稱、參數、列數或錯誤、呼叫者、連線名稱、時間。

後續才把同一組工具交給對談介面與報表範本。對談把一句話收成「哪個連線、哪個 Call、哪些篩選」。範本只描述版面與繫結，不內嵌資料。再下一步，對談決定套哪一份範本。需要語言模型的步驟放在 Python 側車，由 C# 呼叫編譯後的程式；SQL、連線與方言留在現有 C#。

## What Makes This Different

差異來自已經接好的五種資料庫，以及已經註冊的 Call，不是自研模型，也不是新的查詢引擎。跨廠商 SQL planner、自研儲存引擎，架構契約裡本來就不是這套產品的工作。

Agent 呼叫的是具名函數（`query` 的鍵值條件、`count` 的計數），不是一段自由 SQL。這讓方言留在 Provider，也讓稽核讀得懂「查了哪張表、哪些條件」。

資料庫抽象已經在程式裡。`DbServiceFactory` 依 `Sqlite`、`SqlServer`、`MySQL`、`Oracle`、`PostgreSQL` 建立服務。REST 端點只使用這個工廠。文件 [docs/web/index.md](../../web/index.md) 仍寫 `SetupServer` 只啟用 Sqlite，該方法已不在程式裡，屬文件漂移，不代表產品綁定 Sqlite。未設定時的預設名稱是 `Sqlite`，那是預設值。

P0 用外部 Agent 驗證工具面。產品在這個增量不附帶模型。模型可以更換，工具契約保持不變。

## Who This Serves

**P0 的主要使用者是整合方。** 他們維護既有的 C#、REST、GraphQL 或 EZIE 整合，並要把外部 Agent（桌面 Agent、內部 copilot）接到已上線的業務庫。成功是：不改公開的 `IDbService` 簽名，Agent 用同一組工具完成唯讀查詢，換 `ServerType` 與連線字串就能打到工廠已列出的任一引擎。

**業務與分析人員是下一個表面的使用者。** 他們用語句取數、看結果表、匯出。他們在 P0 沒有自己的介面；他們的路徑要等 MCP 工具被對談消費。

**報表設計者更後面。** 他們用拖拉元件與參數做出制式樣式，再讓對談把資料套上去。P0 不交付設計器。

P0 明確不服務：要在對話框貼上連線字串的人、要 Agent 直接執行任意 SQL 的人、要像素級報表排版引擎的人。

## Success Criteria

- 外部 MCP 客戶端對一個已設定連線走完「列出資料表 → 列出欄位 → 鍵值查詢」，並得到列資料。
- 同一組工具，只更換伺服器組態的連線字串與 `ServerType`，可對工廠已列出的五種引擎各完成上述旅程（該引擎有可連線的測試庫）。
- 出貨 P0 時，公開的 `IDbService`／`IDbServiceAsync` 簽名沒有變更。
- 預設廣告與可呼叫集合裡沒有 `insert`、`update`、`delete`、`sql`。
- 抽一筆查詢，稽核紀錄能回答：誰、對哪個具名連線、呼叫了哪個工具、條件是什麼、回了多少列或什麼錯誤。連線字串不出現在工具參數與稽核正文。

反向指標：工具數量變多、或把自由 SQL 開放給 Agent，不算成功。P0 要的是一條可稽核的唯讀路徑。

## Scope

**P0 在範圍內**

- 新增 MCP 宿主，工具對應 `tables`、`fields`、`get`、`query`、`count`、`exists`。
- 具名連線只存在伺服器組態。工具參數收連線名稱，不收連線字串。
- 連線一律經 `DbServiceFactory` 取得 `IDbService`。
- 寫入與 `sql` 預設關閉。
- 每次呼叫的稽核紀錄。

**P0 在範圍外**

- 對談查資料、結果匯出以外的報表版面、拖拉範本、對談套版。
- 結構的業務語言說明、結果敘事、跨來源簡報、需人確認的寫入提案。
- Python 側車。P0 沒有語句要解析，也沒有敘事要寫。側車從對談與範本才開始。
- 更改 Core、Provider、公開資料存取簽名。
- 在產品內附帶或綁定某一個語言模型。

## Vision

兩到三年後，同一條工具面支撐三個表面：外部 Agent、對談取數、制式報表。人說「把這個月的銷貨套到月報」，系統選定具名連線、範本與參數，人確認後才填資料。範本是可重複使用的樣式；資料每次現查。

跨來源的簡報是多次查詢再寫成一段話，不是新的 SQL planner。寫入以提案出現，人確認後才執行。五種資料庫仍由現有提供者負責。AI 應用增加的是意圖、繫結與說明，不是第二套資料引擎。

## AI 應用地圖

排序的理由：先證明外部 Agent 能安全讀資料，再讓人用同一組工具說話、做表、套版。

| 階段 | 應用 | 使用者看見的結果 |
|------|------|------------------|
| P0 | 唯讀 MCP 資料平面 | 外部 Agent 發現並呼叫既有唯讀 Call，換引擎不用換工具 |
| P1 | 對談查資料與產表 | 一句話變成連線、Call、篩選；結果是表與匯出 |
| P2 | 拖拉範本設計 | 元件與參數組成範本；AI 依欄位建議元件與繫結 |
| P3 | 對談套版 | 一句話選定資料來源、範本、參數；人確認後執行 |
| 其後 | 結構說明 | Agent 用業務語言說明有哪些表與欄位 |
| 其後 | 結果敘事 | 列資料回來後，一段摘要與異常提示，數字來自查詢結果 |
| 其後 | 跨來源簡報 | 多個具名連線各查一次，再寫成一份簡報 |
| 其後 | 寫入提案 | Agent 草擬新增或更新，人確認後才執行 |

P1 起，語句解析、版面建議、敘事由 Python 側車負責，C# 呼叫編譯後的程式。側車不執行 SQL，不持有連線。

## 產品原則

REST、GraphQL、MCP 都只透過 `DbServiceFactory` 取得 `IDbService`。宿主不為單一引擎寫分支，也不把某一家資料庫寫進工具或路由。這條原則從 P0 開始生效，後續表面沿用。
