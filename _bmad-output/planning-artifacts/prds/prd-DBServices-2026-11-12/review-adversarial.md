# Adversarial Review — 資料來源註記

審查對象：`prd.md`、`addendum.md`（2026-11-12，status: draft）。對照定稿 `prd-DBServices-2026-10-12/prd.md`（status: final）及其附錄，以及本文件宣稱繼承的資料平面約束（註記站不讀業務列、連線字串留在伺服器）。不改寫 PRD，不提案架構。

## Verdict

這份草稿不能交給架構或拆故事。文首同時寫「三個入口契約維持不變」與「檢視設計改讀已確認的註記包」，定稿 FR-4、UJ-1、第 13 節與附錄仍要求規劃期目錄來自二代平台資料源、且這一讀不經過待轉資料庫；開放問題 8 問的是那條通道，不是准許用一份可以完全不連資料庫的 Excel 註記包把來源換掉。Excel 包與活庫對不上時的發布後果、取代舊包後既有檢視的去留、再讀的身份鍵、確認的最低內容都沒有可測句子；FR-7 又允許分析師自寫關聯，已聲明關聯就不是語意依據。資料平面那兩條繼承約束，這份文件有寫死，問題不在那裡。

## Findings

- **critical** 定稿 FR-4 仍是相反契約，而且新文件自己宣布舊文繼續有效（新 PRD 文首、§4.4、§7 接點 4、§9；新附錄「與既有 PRD 的關係」「已決定的約束」5；定稿 UJ-1、FR-4、§11、§12、§13、開放問題 8；定稿附錄「規劃期的表結構」）— 新文首寫：「既有檢視與報表 PRD 的三個入口契約維持不變。本文件只改規劃期『資料表目錄從哪裡來』：檢視設計改讀已確認的註記包」。同一段先宣布入口契約不動，下一句就改掉模組設計工具的目錄。§9 寫「不改寫檢視與報表 PRD 的檢視／樣式／Chat 契約正文，以其開放問題 8 的產品答案形式銜接」。附錄寫「既有檢視與報表的技術附錄仍有效」，並寫「不改 FR-5～FR-16 正文」。他們把 FR-4 從「不改」清單裡拿掉，卻沒有在定稿裡作廢 FR-4。定稿 FR-4 仍是：「系統分析師在規劃期可看到二代平台資料源的資料表與欄位。」後果：「這份結構不來自待轉資料庫，也不要求先完成轉置。」「沒有資料表時，清單是空的。」UJ-1：「她看到二代平台的資料表與欄位，不是待轉資料庫。」§13：「二代平台資料源：規劃期的表結構從這裡來。讀取通道留給架構。這一讀不經過待轉資料庫。」§12：「系統分析師在規劃期看得到二代平台的表結構。」定稿附錄：「模組設計工具在規劃期讀的是二代平台資料源的表與欄，不是待轉資料庫。」開放問題 8 只問通道：「規劃期讀取二代平台表結構的通道仍未定。」它禁止三件事：用待轉庫 `GET /meta` 充當、為了這份結構讀業務列、把連線字串帶進模組設計工具。它沒有授權更換「二代平台資料源」這個來源，也沒有授權一份從未讀過任何資料庫的註記包。定稿 FR-5 仍寫「每一段關聯要麼是目錄裡的外鍵」，這裡的目錄是 FR-4 的二代平台目錄，不是註記包裡的已聲明關聯。新附錄把舊附錄標成仍有效，等於兩份附錄對「設計工具讀什麼」同時下命。故事若依定稿做，目錄仍是二代平台；若依新 PRD 做，目錄只是已確認註記包。沒有一句寫明定稿哪些句子失效。 *Fix:* 在本 PRD 寫明一份作廢清單：定稿 FR-4、UJ-1 路徑裡「看到二代平台的資料表與欄位，不是待轉資料庫」、§11 執行邊界的「規劃期的表結構通道未定」、§12 與 §13 的「規劃期的表結構從二代平台資料源來」、定稿附錄「規劃期的表結構」、開放問題 8 的「通道仍未定」，改由本 PRD 取代。其餘 FR-5 至 FR-16 若真的不變，逐條標成仍有效；FR-5 的「目錄裡的外鍵」若改指已聲明關聯，就把它列入作廢清單，不要用「不改正文」把舊句留成第二套契約。

- **critical** 「具名連線」回答的不是開放問題 8（新 PRD FR-3、§7 接點 3 與接點 4、§8 問題 4；新附錄「資料庫讀入與 SchemaGraph」；定稿 FR-13、開放問題 8、§13）— 接點 4 宣稱：「本文件回答檢視與報表 PRD 開放問題 8：規劃期結構通道是『已確認註記包』，不是待轉庫的結構端點，也不是未註記的即時連線目錄。」這是換題。開放問題 8 的主詞是「讀取二代平台表結構的通道」。已確認註記包是人確認過的產物，不是二代平台的讀取通道。FR-3 真正去讀結構時，規則是：「恰有一筆組態完整的具名連線才讀取。」這句與定稿執行期 FR-13 的「伺服器恰有一筆具名連線時，呼叫綁定該連線」是同一條規則。定稿把這條規則用在讀列，並把規劃期來源另立為二代平台資料源，且「這一讀不經過待轉資料庫」。新 PRD 從未寫這筆具名連線是二代平台資料源，也從未寫它不是待轉資料庫。附錄只禁止「用待轉庫 `GET /meta` 充當二代平台結構」，這比定稿的禁令窄：不用那個 HTTP 路由，仍可以從同一座待轉庫把結構讀進註記包。零筆或多筆時的行為沿用了，來源身分沒有沿用。故事無法判定「讀到待轉庫的表」是 FR-3 的正確結果還是開放問題 8 的違約。 *Fix:* 寫明註記站從資料庫讀入的那一次，讀的是二代平台資料源的表、欄、型別、主鍵與外鍵，不讀待轉資料庫。具名連線若不是這座來源，拒絕讀取，讀列次數為 0。若 v1 根本無法指向二代平台資料源，就把 FR-3 移出本輪，不要把執行期那筆連線當成開放問題 8 的答案。

- **critical** Excel 可以確認出一份與活庫無關的包，發布與執行期的後果沒被命名（新 PRD 願景、UJ-1、UJ-3、FR-2、FR-5、FR-7、FR-8、§7 接點 3、SM-1、SM-C1；新附錄欄位對應與樣品對照；定稿 FR-6、FR-7）— FR-2：「匯入不讀業務列，也不要求資料庫連線。」FR-5 確認之後「設計階段看得到這一份已確認的包」，沒有要求包內表名存在於任何資料庫。UJ-3 接著讓林可依該包定義檢視並發布，高潮是：「發布後 MCP 目錄出現該檢視，行為與既有檢視與報表 PRD 相同。」FR-8 把建立、修改、發布與 MCP 包裹收成「維持檢視與報表 PRD 的 FR-5 至 FR-7」。接點 3：「已發布檢視的執行期讀列維持現狀。」定稿 FR-6 的發布是分析師確認定義，目錄因此出現該檢視，不檢查來源表是否存在。定稿 FR-7 只說呼叫失敗時不產生動態報表。兩份文件合在一起，仍然沒有寫：註記包的表名、欄名與活庫不一致時，是拒絕發布，還是允許發布、等呼叫失敗。附錄把 DBML 型別定成 H 側 `H_資料類型長度`，樣品對照寫明 `MLST_NO` 的 DBML 型別是 `char(7)`，S 資料長度是 4。`TABLE_DATE`「可無 S 側 G–L」仍納入實體表。設計目錄上的型別與欄集合可以從一開始就不是活庫的結構。FR-7 與 SM-C1 還禁止設計端靠即時連線結構繞過確認，於是設計期不準對帳，發布期也沒有對帳句子。SM-1 只核對 Excel 與樣品 DBML 的文字，不要求這份包能被已發布檢視讀到列。附錄沒有寫 `S_檔案名稱` 等於執行期可查詢的表名，也沒有寫 `S_欄位名稱` 等於執行期可查詢的欄名；樣品表名是 `LH_TXN_MLST`，表註卻寫來源檔 `T_LH_TXN_MLST`，欄註同時留下 H 名 `POST_BRH_NO`。三個名字哪一個會被放進檢視的來源表，文件沒有選。 *Fix:* 寫明檢視保存與發布使用的表名、欄名就是註記包的實體表名與實體欄名。這兩個名字必須在執行期那筆連線的結構裡存在，型別以該連線的結構為準；對不上則拒絕發布，已存在的檢視定義不變。字典 H 側型別、S 側長度與無 S 側的列只進註解，不進可發布的來源欄。Excel 路徑可以在沒有資料庫時做草稿，不可以在未對上活庫時確認成設計目錄。

- **high** 新確認取代舊包時，已定義檢視的去留是沉默的（新 PRD UJ-4、FR-6、§8 問題 2、§9、§10；定稿 FR-5、FR-6）— §8 問題 2 先承認多份已確認包「仍未定」，接著用假設把問題收成選擇介面：「v1 一次只啟用一份已確認包；新確認可取代先前啟用的包，並在確認當下提示。」UJ-4 只寫「再次確認後，設計端改看新包」與「她放棄草稿。已確認的包維持原樣。」§10 只保護失敗路徑：「確認失敗時，已確認的包與已保存的檢視定義不變。」確認成功而且發生取代時，沒有對應句子。沒有寫檢視綁的是包的識別，還是表名與欄名。沒有寫已發布檢視是否仍留在 MCP 目錄、仍可被呼叫、仍可被修改目的文字。定稿 FR-5 寫被樣式範本引用的檢視「不能刪除、不能取消發布，也不能改名稱、輸出欄或參數」。新 PRD §5 與 FR-8 宣布不改樣式範本。因此一次成功的新確認可以讓設計目錄換成另一包，而舊檢視既不能下架、也不能改欄，目錄卻已不再列出它們的表。提示要提示什麼——將被取代的包、受影響的檢視名稱、或只是一則成功訊息——沒有可觀察內容，測試無法失敗。「取代」也沒有寫舊包是封存、退回草稿，還是刪除，以及確認之後能否回到上一份已確認包。v1 只有一份啟用包時，確認一份郵務清單會把定稿 UJ-1 那種銷貨目錄整份擠掉；這個後果不在問題 2 的問句裡。 *Fix:* 寫明新確認若會使任一已保存檢視的來源表、輸出欄或關聯端點不再落在新包內，則拒絕確認，並在拒絕訊息列出這些檢視的名稱；舊的已確認包與這些檢視維持原樣。不因確認而取消發布、刪除或改寫檢視。提示出現在確認之前，操作者取消則不取代。要同時保留兩份已確認包，就刪掉 v1 的取代假設，不要留成未定。

- **high** 「同名」不是可實作的身份鍵（新 PRD UJ-4、FR-6、SM-4、§8 問題 3；新附錄「列到 DBML 欄的對應」與樣品對照）— FR-6：「同名表與同名欄保留原註記。」「新增、刪除、型別改變另列可見。」沒有寫比較鍵。附錄把表名定為 `S_檔案名稱`、欄名定為 `S_欄位名稱`，但 FR-6 的「同名」沒有引用這兩個欄，也沒有排除 H 側 `H_欄位名稱`。改名因此沒有產品行為：若身份只是名稱，改名會變成刪除加新增，原註記消失；文件沒有承認這就是規則，故事就會自作模糊配對。大小寫沒有寫。`OFFICE_CODE` 與 `office_code` 是同一欄還是一刪一增，無法測。差異清單只有新增、刪除、型別改變。H 欄名、畫面格式、可否空白、唯一索引勾記、主鍵、外鍵、註解原文的變化都不在清單裡；依「同名保留原註記」，這些變化會被吃掉，操作者看不到字典已經改了說明。型別改變也沒有寫比的是正規化後的 H 側型別、S 側長度，還是資料庫型別。無 S 側的列，附錄只說「欄名用 H／既有對應規則產出樣品中的 `TABLE_DATE text`」，規則本身不存在。再讀時若該列補上 S 側欄名，身份鍵會從 H 名跳到 S 名，註記被當成刪除加新增。UJ-4 的再讀是來源庫；FR-2 的成功再匯入沒有指向 FR-6。Excel 再匯入是整份重產草稿，還是對上一份做同名合併，沒有句子。「原註記」也沒有寫來源是上一份已確認包，還是當下這份草稿；兩者都在而且內容不同時，合併基底要由故事發明。§8 問題 3 只把另一種活頁簿版型推出本輪，沒有處理同一契約的多工作表：多張符合契約的工作表是全部進同一包、只取第一張，還是直接拒絕，未寫；兩張工作表出現同一個 `S_檔案名稱` 也未寫。 *Fix:* 寫明再讀的比對鍵是實體表名加實體欄名，兩者皆為去除首尾空白後的區分大小寫精確字串，用 S 側名稱；S 側欄名空白時該列不進實體欄。改名就是刪除加新增，原註記不自動搬家。差異清單除了新增、刪除、型別，還包含可否空白、主鍵、外鍵、唯一索引勾記、H 欄名與註解原文。保留的註記以當下草稿為準，草稿沒有該欄時才抄上一份已確認包。多工作表：每一張符合契約的工作表納入同一草稿；任一張對不上或實體表名重複，則整份拒絕，既有草稿不變。Excel 再匯入與資料庫再讀使用同一條規則。

- **high** FR-7 把已聲明關聯從語意依據降成可選建議（新 PRD 願景、詞彙「已聲明關聯」、UJ-3、FR-4、FR-7；定稿 FR-5；新附錄「與模組設計工具的接點」）— 願景：「確認後的 DBML 成為後續所有設計階段的結構與語意依據。」詞彙把已聲明關聯定義成「註記包內由人寫明的表間關係」，理由是「並可附理由」，理由不是必填。UJ-3 高潮：「她選的來源與關聯都落在註記包內。」這句可以讀成選中的關聯必須是包裡那幾條。FR-7 把口子打開：「每一段關聯要麼是註記包內已聲明的關聯，要麼是分析師寫明並接受且仍落在註記包表欄內的關聯；否則拒絕保存」。拒絕條件只剩下端點不在包內，或分析師沒有寫明並接受。包裡沒有聲明這兩欄的關係，分析師仍可保存。已聲明的是 A.x 到 B.y，分析師仍可另寫 A.y 到 B.x 並接受。自寫關聯要寫的內容沒有欄位，不要求理由，也沒有寫它會不會寫回註記包。下一個人在設計目錄看到的已聲明關聯因此可以與已發布檢視實際使用的關聯不同。定稿 FR-5 的「目錄裡的外鍵，或分析師寫明並接受的關聯」被附錄保留為不改的正文；依定稿，人補上的、庫裡沒有的外鍵還不算「目錄裡的外鍵」，分析師仍得再接受一次。依新 FR-7，已聲明關聯又不是唯一可保存的路徑。兩讀都不讓已聲明關聯當語意真理。願景要求的「關聯為什麼這樣連」在自寫這條路徑上可以是空的。 *Fix:* 寫明兩張以上來源表時，每一段關聯必須等於註記包內某一條已聲明關聯的兩端表與欄，否則拒絕保存，既有檢視定義不變。分析師不可另造關聯。已聲明關聯的理由必填。定稿 FR-5 的「或是分析師寫明並接受的關聯」列入作廢清單。

- **high** 「確認」沒有可失敗的完成條件，空包也算做完（新 PRD 詞彙「確認」、UJ-1、FR-4、FR-5、FR-7、SM-2）— 詞彙：「確認 — 資料治理人員把草稿標成可供設計使用。」FR-5 的可測後果是草稿不進設計工具、確認後設計階段看得到、匯出不含業務列與連線字串、不寫回來源庫。沒有一條會因為整包功能說明是空的、表數是零、欄註是空的、關聯沒有理由、或從未匯出 DBML 而拒絕確認。UJ-1 的「補上整包功能說明」「匯出 DBML 核對」「核對無誤後她確認」是敘事，不是閘門。FR-3 明示從資料庫讀入時「註解預設空白」，FR-4 只說「可編輯」，沒有說確認前必須編過。SM-2 只驗證人有補上內容時那些內容還在，不驗證空內容被拒絕。FR-7 的空狀態只覆蓋「沒有已確認註記包」：「清單是空的，並說明資料來源尚未註記。」一份已確認、零張表的包不是這個狀態。清單同樣是空的，那句說明卻是錯的，替代說明不存在。故事可以做成一顆把 `draft` 改成 `confirmed` 的按鈕，並讓 SM-3 通過。願景裡的「可交給設計使用」無法被測成失敗。 *Fix:* 寫明確認必須同時滿足：整包功能說明非空白、至少一張表、每張表至少一個欄、每個欄的註解非空白；有兩張表以上時每一條已聲明關聯的兩端與理由都有值。任一不滿足則拒絕確認，狀態維持草稿。已確認且零張表這個狀態不存在。尚未匯出不阻擋確認；設計目錄以確認當下的註記包為準。

- **medium** 成功的再次匯入沒有規則，FR-2 只規定失敗（新 PRD UJ-1、FR-2、FR-6）— UJ-1 邊緣只寫契約對不上時拒絕匯入、既有草稿不變。FR-2 成功路徑是「產生註記草稿」。第二份成功的 Excel 是覆寫現有草稿、對現有草稿做 FR-6 合併，還是再開一包，沒有寫。已確認包存在時，成功匯入是否一定落在草稿、是否會直接取代已確認包，也沒有寫。FR-6 的「未再次確認前設計目錄不變」只保護確認後的設計端，不保護當下草稿裡已手改的註記。 *Fix:* 寫明成功匯入一律寫入草稿，不改變已確認包。已有草稿時，成功匯入沿用 FR-6 的同名合併，不另開第二份草稿；操作者若要丟掉手改內容，必須先放棄草稿。

- **medium** 設計目錄的欄位少於註記包，假唯一索引到不了分析師手上（新 PRD 詞彙「註記包」、FR-3、FR-4、FR-7；新附錄索引列）— 詞彙寫註記包含「索引語意」。FR-4 要求能保留「有勾唯一索引」以及「它不是真正的唯一鍵」。FR-7 規定設計清單的內容是「表、欄、型別、註解與已聲明關聯」，沒有索引、主鍵、可否空白。樣品把「不是唯一鍵」寫在表級 Note，所以這一份樣品可能靠表註解僥倖出現；FR-3 從資料庫讀入只帶「表、欄、型別、主鍵、外鍵」，不帶唯一索引勾記，也不產生那句表註。資料庫路徑確認之後，分析師看不到「這組欄不是真正的唯一鍵」。Excel 的勾記與資料庫的主鍵在同一套模型裡誰覆蓋誰，FR-6 的差異清單也沒有索引這一列。 *Fix:* 寫明設計清單除了表、欄、型別、註解與已聲明關聯，還顯示主鍵、可否空白，以及每一條索引的欄與索引註解。索引註解必須含「是或不是真正的唯一鍵」。資料庫讀入帶出主鍵與唯一約束；Excel 的勾記只作為索引註解，不標成主鍵。

- **medium** 確認時到底凍結註記包還是 DBML，兩份核對本可以分叉（新 PRD 詞彙「DBML」、FR-5、SM-1；新附錄「註記包形狀」與設計端消費欄位）— 詞彙：「確認與匯出都以它為人與後續工具核對的格式。」FR-5 把匯出與確認寫成兩件都能做的事，沒有寫確認會重新產生 DBML，也沒有寫確認後禁止再改草稿而不改那份已匯出的文字。附錄的包內同時有結構化欄位與一個 `dbml` 字串，又寫「設計端主要消費 `name`／`type`／`note`／`links`」。人可以先匯出、再改欄註、再確認。SM-1 核對的是匯出文字對上樣品，FR-7 讓設計工具讀的是包的欄位。兩份內容不一致時，哪一份是「確認過的檔案」，願景沒有選。 *Fix:* 寫明確認時以註記包的表、欄、型別、註解與已聲明關聯為準，並在同一動作重新產生 DBML；設計工具不讀確認之前匯出的舊檔。確認之後要改內容，只能改草稿，已確認包維持到下一次成功確認。

- **medium** 設計目錄清空時，已發布檢視仍在 MCP 裡，這段切換沒被承認（新 PRD UJ-3 邊緣、FR-7、FR-8；定稿 FR-6、UJ-1）— FR-7：「沒有已確認註記包時，清單是空的，並說明資料來源尚未註記。她不能靠即時連線結構繞過。」FR-8 同時維持定稿的發布規則：MCP 目錄的名稱集合等於已發布檢視。定稿 UJ-1 的銷貨月檢視若已發布，本 PRD 上線當下設計清單是空的，該檢視仍可被呼叫。文件沒有寫這是預期的過渡，也沒有寫分析師還能不能打開這筆檢視改目的文字。目的文字在定稿 FR-5 是樣式引用期間仍可改的欄位；新目錄不認識它的來源表時，編輯器能不能開啟，沒有句子。 *Fix:* 寫明沒有已確認包時，模組設計工具不提供新的來源表，既有已發布檢視仍留在 MCP 目錄，執行期規則不變。這些檢視仍可修改目的文字；來源表、關聯、輸出欄與參數在所屬表欄重新落進已確認包之前不能改。
